# AI Radar｜反馈与订阅实现方案（定稿方向 v2）

- 站点：https://ruiyaoe-hash.github.io/ai-radar/
- 仓库：GitHub Pages 静态站 + Actions 部署
- 版本：v2（吸收外部评审；否决「飞书 webhook 当写入通道」与「每次投票热写 git」）
- 状态：方向已定；第 0 步可立刻做；Worker+D1 视参与率再投入

---

## 0. 相对 v1 的结论变化

| v1 | v2 |
|----|-----|
| 写入候选 A：浏览器 → 飞书入站 → 汇总进仓库 | **否决**。Webhook 暴露在前端≈密钥公开；跨域与刷群问题；用聊天记录当库脆弱 |
| 写入候选 B：Worker 每次投票改 `votes.json` 并部署 | **否决热写 git**。并发 409、污染历史、与 digest 抢 `main`、扩大写凭据面 |
| 页面公开展示赞/踩绝对数 | **早期不展示**；达样本量后再考虑比例 |
| 二元 👍/👎 | 改为 **有用 / 没用 / 有误或漏报**，可选「为什么」 |
| 赞踩与访问统计解耦 | **第 0 步合并**：先用无 cookie 统计的自定义事件验证参与率 |
| 「数据在 GitHub」= 热数据进仓库 | 改为 **热数据在专用存储，每日聚合快照回仓库** |

保留并加强的判断：单卡 / 整站 / 订阅三条链路拆开；不手填卡片 ID；赞踩是趋势信号不是 A/B；Pages 不能安全直写。

## 1. 目标

| 目标 | 说明 |
|------|------|
| 单卡质量信号 | 读者对单条推送表达有用 / 没用 / 有误·漏报，供**运营校准**（信源记分、P0、更正），不是读者社交数字 |
| 整站长反馈 | 飞书问卷：开放题 + 可选「从哪知道我们」+ 可选联系方式 |
| 订阅 | 飞书群；不做邮件 |
| 低摩擦 | 不手填 `card_id`；不依赖飞书 URL 预填 |
| 数据归属 | 可审计的**日快照**进 GitHub；热写入不进 git |
| 阶段匹配 | 读者少时先验证「有没有人用」，再上专用后端 |

**建议成功标准（可改）：** 两周内「投票读者 ÷ 访问读者 ≥ 2%」，且至少产出一条因反馈而改动的信源或分级决策。达不到 → 优先人工访谈，不加基础设施。

## 2. 产品形态

### 2.1 侧边栏：整站反馈（零后端，可先上）

- 目录末：`反馈 / 建议` → 飞书问卷
- 题型：开放题为主；可选单选「你从哪里知道我们」；可选留联系方式
- **删除**卡片 ID、渠道预填依赖

### 2.2 飞书订阅群（零后端，可先上）

- 侧栏或页脚入口
- 上线前确认：邀请链接/二维码有效期、人数上限、外部成员是否可进；入口失效要有巡检

### 2.3 单卡反馈按钮

主操作最多三个：

- **有用**
- **没用**
- **有误 / 漏报**（高价值，直连更正与漏报审计）

点击后：

1. 前端乐观更新 UI → 文案「已记录，谢谢」（**不显示赞踩数**）
2. 可选展开一次「为什么」（不强制）：如 `known | irrelevant | wrong | shallow | missed`
3. 上报见第 3 / 4 节

早期**不公开展示**绝对数或比例（数字小、从众、诱刷、信号主要给运营看）。单卡去重读者数 ≥ 阈值（建议 10）后再考虑展示比例。

## 3. 第 0 步（推荐立刻做）：统计自定义事件

把赞踩与访问统计**合并起步**，验证参与率：

```text
读者点 有用/没用/⚑
  → 前端发无 cookie 统计事件，如 vote/up/<card_id>
  → 统计服务自带基础防刷
  → 每日 Actions 经其 API 导出 → data/feedback/YYYY-MM-DD.json（仅聚合）
```

| 优点 | 缺点 |
|------|------|
| 无自建后端、前端无密钥 | 去重 / 改票 / 原因码较弱 |
| 两周可验证有没有人用 | 达标准后再上 Worker+D1 |

候选工具：GoatCounter、Umami 等（最终选型以大陆可达、无 cookie、自定义事件、API 导出为准）。  
CSP：`connect-src` 加入该统计域名。

---

## 4. 达标后的正式架构：Worker + D1 热存储 + 每日快照回仓库

```text
读者点 有用/没用/⚑
  → 前端乐观更新；POST 到 Worker（**自有域名**，不用 workers.dev）
  → Worker：校验 Origin、card_id∈已知集合、体积极限、按 IP 哈希（日盐）限流
  → 写入 D1：每 (card_id, voter_hash) 只保留最新一票（可改票）
  → 前端需要读聚合时走 Worker（边缘缓存）；默认页仍可不展示数字

每日定时 Actions（避开 08:00 digest）
  → 用 **仅存在于 Actions Secrets** 的令牌调 Worker 导出接口
  → 提交 data/feedback/YYYY-MM-DD.json（仅聚合，无读者标识）
```

安全要点：

- **仓库不放写入 token；Worker 不持有 GitHub 凭据**；Actions **反向拉取**，权限方向更安全
- **无热写 git**：一天一次反馈快照，不与内容提交抢 `main`
- 异常流量再启 Turnstile；默认不加验证码
- 大陆：自有域名 + 上线前大陆网络实测；失败则前端本地排队重试；若仍差，同接口迁国内云函数，模型不变

### 4.1 D1 示意

```sql
votes(
  card_id      TEXT,
  voter_hash   TEXT,   -- 浏览器本地随机 ID 的哈希；不用 cookie、不用指纹
  vote         TEXT,   -- up | down | flag
  reason       TEXT,   -- 可选：known | irrelevant | wrong | shallow | missed
  ref          TEXT,
  updated_at   INTEGER,
  PRIMARY KEY (card_id, voter_hash)
)
```

不用浏览器指纹（不稳定且有隐私问题）。

## 5. 使用闭环（收了必须用）

每周（或每 digest 周期）把反馈与卡片元数据关联：

- 信源 handle、优先级、lens、tag、`card_id`
- 输出：**信源记分调整建议**、**P0 校准**、**有误清单 → 更正流程**、**漏报清单 → 漏报审计**
- 「有误 / 漏报」优先级高于普通有用/没用

否则赞踩只是装饰数字。

## 6. 前置依赖与实现细节

| 项 | 说明 |
|----|------|
| `card_id` 稳定 | 投票键必须是稳定 `id`（现有 archive 已用 `id`，如 `evt-…`），更正/合并/归档页不得改键；若仍有以 URL 为键的路径须先收敛 |
| CSP | 统计域名、日后 Worker 域名写入 `connect-src` |
| 防刷 | 第 0 步靠统计服务；正式版上线即基础限流，不做「几乎不防」 |
| 飞书群入口 | 确认有效期与外部加入限制；定期巡检 |
| 与 digest | 反馈快照 cron 避开 08:00 内容提交窗口 |

## 7. 明确不做

- 浏览器直打飞书入站 webhook 当投票写入
- 每次投票 commit / 部署 Pages
- 早期公开展示赞踩绝对数
- 必填手填卡片 ID；依赖飞书 URL 预填
- 邮件订阅；以 Tally 等为赞踩主路径
- 浏览器指纹防刷

---

## 8. 实施顺序

1. **确认** `card_id` 全链路稳定；规划 CSP 白名单扩展点  
2. **零后端先上**：侧栏整站飞书问卷 + 飞书群入口（确认链接可用）  
3. **第 0 步**：无 cookie 统计 + `vote/.../<card_id>` 事件；跑约两周看参与率  
4. **参与率达标** → Worker + D1 + 每日快照；大陆实测通过  
5. **同步闭环**：周报把投票×元数据 → 信源记分 / 有误·漏报清单 → 更正流程  
6. 再对外宣称「欢迎反馈」

## 9. 拍板结论（相对原 5 问）

| # | 结论 |
|---|------|
| 1 写入通道 | 不选 A/B；**第 0 步统计事件** → 达标后 **Worker+D1+日快照** |
| 2 展示 | **早期都不展示**；达阈值后再考虑比例、不展示绝对数 |
| 3 改票 | **允许改票**；每读者每卡保留最新一票 |
| 4 问卷 | **开放题 + 可选来源单选 + 可选联系方式**；去掉卡片 ID 题 |
| 5 防刷 | **上线即基础限流**（第 0 步用统计服务能力） |
